# 2026-10-10：車2 硬體 PWM（analogWrite）+ 編碼器回授 最簡單測試

**問題：** 正式版 `car2_car_control.ino` 的 D8/D9 是 `micros()` 手刻的軟體 PWM，`loop()` 被 `sendStatus()`（單次約 1.1 ms，馬達轉時最大 2~3 ms）之類的長函式佔住時，PWM 會跟著凍結。`書面資料/技術文件/architecture/wiring_plan.md` 記載早期 `analogWrite()` 在 D8/D9 上「實測沒有動作」，根因沒查出來。有可能只是當時接線沒插好。這支程式回答：**現在這組接線，`analogWrite()` 驅動 D8/D9 時，編碼器有沒有回授？**

## 用法

```
arduino-cli compile --fqbn HT32:HT32:BM53A367A firmware/car2/investigations/2026-10-hw-pwm-test/car2_hwpwm_encoder_test
arduino-cli upload  --fqbn HT32:HT32:BM53A367A -p COM10 firmware/car2/investigations/2026-10-hw-pwm-test/car2_hwpwm_encoder_test
```

序列埠 115200，開機**不會自動轉**。**輪子一定要離地**（L298N 無過流保護）。**測完要燒回** `firmware/car2/car2_car_control/car2_car_control.ino`。

| 步驟 | 指令 | 判讀 |
|---|---|---|
| 1. 編碼器 | 不下指令，用手轉輪子 | 序列埠印出 `[enc] L= R=` 且數字會變 = 編碼器線與中斷正常（不需要馬達電源） |
| 2. 硬體 PWM | `l`（左輪 D9）、`r`（右輪 D8） | 看「前進計數」是否 ≥ 50 ticks，並看計時器暫存器那幾行 |
| 3. 對照組 | `s` 切軟體 PWM 後再 `l` / `r` | 同 duty、同 5 kHz，用舊做法驅動 |

其他指令：`b` 兩輪、`x` 中止、`+`/`-` duty ±10（預設 160）、`1`/`5` 切 1 kHz / 5 kHz（預設 5 kHz，正式版前饋表是 5 kHz 校正的，核心預設是 1 kHz）、`h` 回硬體 PWM、`?` 說明。

## 結果怎麼判讀

| 現象 | 意思 |
|---|---|
| 手轉有計數；`s` 有轉有 ticks；`h` 沒 ticks | 問題在 `analogWrite()`，看計時器暫存器那幾行（CCR 是否等於預期） |
| 手轉有計數；`s`、`h` 都有 ticks | `analogWrite()` 現在可用，上次多半是接線；可以進下一步改正式版 |
| 手轉沒計數 | 編碼器線 / 中斷腳，先解這個 |
| 手轉有計數；`s`、`h` 都沒 ticks | 馬達電源 / 驅動板 / 方向腳 / PWM 線，不是 `analogWrite()` 的問題 |
| ticks 為負 | 有回授但方向相反（A/B 相或馬達極性） |

## 事前從核心原始碼讀到的事（HT32 core 1.3.0，`variants/BM53A367A/variant.c`、`cores/HT32/wiring_analog.c`）

- **D8 → PWM0 計時器 CH0；D9 → MCTM0 計時器 CH0N（互補通道）。** 是兩顆不同計時器，沒有共用。D9 走的是互補通道路徑（`pwm_start()` 裡 `MCTM_ChannelNConfig`），核心原始碼那一段還留著 `// Why?` 註解，是比較脆弱的路徑。
- `analogWrite()` 每次呼叫都會 `TM_SetFrequency()`，再用 `TM_SetCompare()` 讀 `TM->CRR` 算比較值。而 CRR 有開預載（preload），第一次呼叫時讀到的可能還是舊的重載值（0xFFFF），導致**第一次的 duty 不對、之後才修正**。這是讀程式碼的**推測，沒有驗證**。測試程式因此每 20 ms 重呼叫一次（模擬正式版 PID 週期），並印出計時器暫存器，不用示波器就能看出 CCR 有沒有算對。
- 互補通道若輸出極性是反的，`analogWrite(pin, 0)` 反而會變成全開。測試程式停止時**先把方向腳全部拉低**再設 PWM 0，所以不會因此轉動。**要把 D9 用在正式版之前，這點必須驗證**（不要只看有轉就算過）。
- 這支測試**不會**證明「PWM 腳實際波形正確」，只證明「馬達有被驅動、編碼器有回授」。要看波形需要示波器或邏輯分析儀。

## 這支測試沒涵蓋的

- 只測正轉，沒測反轉。
- 沒測轉速與 duty 的關係：換成硬體 PWM 後，前饋查表（`FF_LUT_*`）是軟體 PWM 5 kHz 校正的，**需要重新量一次**。
- 沒測 PWM 解析度：核心預設 8 bit（0~255），硬體 PWM 在 5 kHz 下實際 CRR≈14399，解析度比 255 級高，但 `analogWrite()` 介面仍是 0~255。
- 沒進正式版：正式版仍是軟體 PWM，這個資料夾沒有動 `car2_car_control.ino`。

# 實測結果（2026-10-10 11:56，輪子架空，duty 160，每次驅動 2 秒）

原始記錄 `results/hwpwm_raw_20261010_run1.log`，彙整 `results/hwpwm_summary_20261010_run1.json`，執行腳本 `host_tools/hwpwm_run.py`。

|---|---|---|---|
| 硬體 PWM 5 kHz | 7540 ticks，175.5 rpm | 7524 ticks，175.1 rpm | 7494 / 7596 |
| 軟體 PWM 5 kHz（對照組） | 7630 ticks，177.6 rpm | 7743 ticks，180.2 rpm | 7425 / 7609 |
| 硬體 PWM 1 kHz | 10554 ticks，245.7 rpm | 10880 ticks，253.2 rpm | 10370 / 10731 |

- **9 次驅動全部有回授**，沒有任何一次被防堵轉中止，方向（前進為正）全部正確。閒置 3 秒基線沒有任何計數。
- **硬體與軟體 PWM 在 5 kHz 幾乎一致：** 同 duty 下左輪 99.9%、右輪 98.5%，在 trial 之間的散佈（約 ±1.5%）以內。
- **計時器暫存器全部吻合：** 5 kHz 時 D8、D9 都是 CRR=11999、CCR=7529（duty 160 的預期值就是 7529）；1 kHz 時 CRR=59999、CCR=37647（預期 37647）。
- **D9 互補通道（MCTM0 CH0N）極性沒反：** 它的轉速與 D8 相同。如果極性反了，duty 160 會變成約 37% 的有效 duty，轉速會明顯低很多。
- **起轉階段兩種 PWM 相同：** 第一個 200 ms 視窗硬體 +256 / +265、軟體 +255，沒看到「第一次呼叫 duty 算錯」的現象（推測的 CRR 預載問題在這個測試裡沒有觀察到，若存在影響不超過一個 20 ms 更新週期）。
- **PWM 頻率對轉速影響很大：** 同樣 duty 160，1 kHz 比 5 kHz 快約 40%（246 vs 176 rpm）。所以前饋查表只能用在 5 kHz；換成硬體 PWM 必須維持 `analogWriteFrequency(5000)`，否則整張表失準。成因沒有查，不要猜。

## 這個結果能說明什麼、不能說明什麼

- 能說明：現在這組接線與這片板子，D8、D9 用 `analogWrite()` 都能正常驅動馬達，編碼器有回授。
- **不能說明上次為什麼沒動。** 早期紀錄是「完整韌體流程中 `analogWrite()` 沒有反映在輸出」，這次是獨立的最小測試，沒有重現。可能是接線、也可能是完整韌體裡的某個交互作用。**要換進正式版之前，必須在完整韌體上再驗一次。**
- 腳位檢查（讀 `variant.h`）：Serial3 用 PA4/PA5（USART1）、Wire1 用 PC12/PC13，D8/D9 是 PA14/PA15，三者沒有腳位重疊。PA14/PA15 同時是 Wire5 的腳位，但正式版沒有用 Wire5。
- 沒測：反轉、低 duty（起轉門檻與遲滯）、地面負載、與 `sendStatus()` 同時運作時的凍結改善程度。

## 沒解決的、沒驗證的

- **100% 大階梯（90 → 270 rpm）仍過衝約 7%（+19 rpm）：** P 項把 duty 推到 255 飽和，馬達約 0.3 s 的機械延遲讓速度衝過目標，之後被拉回。不是積分造成（積分分離也救不了），KP / KI / 限速都改不掉；先接受。
- **限速 12 的瞬間電流沒有量測。** L298N 無過流保護。上地面後若驅動板或電源異常發熱 / 跳電，先把 `MAX_DUTY_STEP_PER_CYCLE` 調回 6~8。
- **全部在輪子架空下調的。** 上地面有負載後曲線右移，KI、kick 強度、`MIN_RUN_DUTY` 都需要重量。「前饋偏移」的模擬在偏移 −20 duty 時會誤觸低速 ON/OFF 模式（前饋掉到 `MIN_RUN_DUTY` 以下），結果不可信，只當定性參考。
- 左右差動 20/40 的左右輪獨立性只看了一組。反轉方向的 PID 響應沒測。
