# 2026-10-10：Turbo 模式（供電 14 V → 14.5 V，短時間超過 270 rpm）——韌體已寫好，**尚未上板、尚未實測**

**背景：** 車2 要當「魔王車」，希望短時間能衝到 300 rpm 以上。100% 指令 = 270 rpm（116 ticks/20 ms）。10/10 在約 14 V 供電、輪子架空量到全速（duty 255）左輪約 300、右輪約 306 rpm。使用者打算把供電調到 14.5 V 試試看。

**寫的時候 BMduino 沒接上**：韌體原始碼已改好並編譯通過（51,080 B），**沒有燒錄、沒有量任何東西**。下面所有「預期」都是推論，標明了依據；實際行為以上板結果為準。

## 韌體改了什麼（`car2_car_control.ino`，備份 `.v12_pre_turbo_20261010.bak`）

| 項目 | 內容 |
|---|---|
| 命令範圍 | `bwl` / `bwr` 正向從 ±100 放寬到 `-100 ~ +125`（`TURBO_CMD_MAX_PCT`）。**後退仍是 -100**。101~125 是 turbo，轉速線性延伸（每 +1 約 +2.57 rpm） |
| 預設行為 | **不變**：命令 ≤ 100 時完全一樣（離線模擬：從不要求 turbo → 預算一直滿、不鎖定）。Orin 端 `uart_bridge_node` 的 `max_wheel_speed` 目前夾在 100，所以不改 Orin 就不會進入 turbo |
| 時間限制（韌體端，不靠 Orin 自律） | 預算制：連續 turbo 最多 `TURBO_MAX_MS`=3000 ms；用完鎖定（>100 一律夾回 100）；鎖定後要「不要求 turbo」累計到預算回到 1500 ms 才解除（約 5 s），從 0 充滿 10 s。**鎖定中如果 Orin 還一直要求 turbo，不放行也不充電**——上層卡在 112 也只有一次 3 s |
| 目標上限 | turbo 區間的目標轉速不超過「前饋表在 duty `TURBO_FF_DUTY_CEILING`=250 時的轉速」（保留 5 duty 給 PID），也不低於 100% 的目標 |
| 觀測 | 只加在 USB dbg 行尾：`turboState`（0 沒用、1 放行中、2 鎖定）、`turboBudgetMs`（22 → 24 欄）。**STA 協議沒動**。注意：不要用 STA 的 `f` 欄位回報 turbo 狀態——Orin 的 `MotorFaultGate` 把 `f != 0` 當堵轉故障、會把輪速指令壓成 0 |
| 沒動 | 堵轉切斷、反轉保護、指令逾時、PID、前饋表、硬體 PWM 5 kHz |
| **總開關** | `TURBO_CMD_MAX_PCT` 改成 `100` 就等於完全關掉 turbo（命令會被夾回 ±100） |

### 離線模擬（Python 逐 tick 移植，20 ms/tick；沒有主機端 C++ 編譯器，所以邏輯是移植版不是原碼本身）

| 情境 | 結果 |
|---|---|
| 開機後持續要求 turbo 6 s | 放行 149 tick = 2.98 s，之後鎖定；再持續要求 10 s 放行 0 tick（不充電） |
| 降回 ≤100 | 250 tick = 5.0 s 後解除鎖定；充滿要 10 s |
| 解除後立刻再要求 | 放行 74 tick = 1.48 s 又鎖 |
| 每 0.5 s 要求 0.1 s（20%） | 全部放行、從不鎖定 |
| 每 1 s 要求 0.5 s（50%） | 30 s 內只放行 11.5 s（可持續上限約 23%） |
| 從不要求 | 預算 3000 不動、不鎖定（=今天的行為） |

## 預期（推論，**不是實測**）：14.5 V 能不能超過 300 rpm？

目前（約 14 V 校正）的前饋表算出來的 turbo 上限（duty 250）：**左輪 291 rpm、右輪 297 rpm**，duty 255 是 300 / 306 rpm。也就是說**今天這個表和供電下，turbo 到不了 300**（命令 112 ≈ 300.8 rpm 的目標會被夾在 291 / 297）。

| 命令 | 目標 rpm | 目前表的實際上限（左 / 右） |
|---|---|---|
| 100 | 270.0 | 270.0 / 270.0 |
| 108 | 290.5 | 290.5 / 290.5 |
| 110 | 295.7 | 291.2 / 295.7 |
| 112 | 300.8 | 291.2 / 297.0 |
| 115 / 120 / 125 | 308 / 321 / 334 | 291.2 / 297.0（被夾住） |

粗估：轉速約正比於馬達端電壓。供電 14 → 14.5 V（+3.6%）後，duty 250 的轉速約 **左 301、右 307 rpm**；全速約 311 / 317 rpm。**也就是說，剛好在 300 的邊緣**，而且：
- 「約 14 V」從來沒有精確量過（硬體摘要記的是 12 V 實驗室電源，校正時調到「約 14 V」）。實際電壓差多少，結論就偏多少。**上板第一件事是用三用電表量 L298N 的 VS 端電壓（空載、100%、turbo 負載下各一次）**。
- 這只是輪子架空的空載轉速。地面有負載後曲線右移，300 rpm 很可能到不了。
- duty 250 以上沒有控制餘裕：PID 在頂端等於開迴路，轉速會隨電池電壓下降而掉。

## 上板檢查清單（照順序做，前一步不合格就停）

**0. 硬體準備與風險（升電壓前，由你確認）**
- 馬達額定 12 V（操作範圍 6~12 V，空載 313 ± 31 rpm）。目前約 14 V 已在額定之上（L298N 會吃掉約 2~3 V，馬達端實際比供電低）；14.5 V 再高 0.5 V，風險是繞組發熱——turbo 是短時間，但要量。
- L298N 每通道約 2 A（尖峰 3 A）、**沒有過流保護**；堵轉電流正比於電壓（23 A@12 V → 14.5 V 約 28 A）。韌體的堵轉切斷是 600 ms，電壓越高越危險。
- **用有限流功能的實驗室電源，電流限制先設 3~4 A**，再看實際峰值。Orin / BMduino 如果共用同一個供電，先確認它們的輸入電壓範圍。
- 輪子離地。L298N 要有散熱片，最好加風扇；每個步驟後摸溫度或用紅外線測溫。

**0.5 先量 L298N 吃掉多少電壓（驗證「馬達端實際比供電低」這個假設，2026-10-11 加）**
- 假設：馬達端電壓 = 供電電壓 − L298N 壓降，所以供電 14.5 V 時馬達端不一定超過額定 12 V。目前只有推論，沒有量測。
- 用開迴路韌體送 duty 255（全開通，輸出是直流，三用電表才讀得準；duty < 255 是 5 kHz PWM，電表平均值不可信，要用示波器）。
- 同時量：(a) L298N VS 端子對 GND；(b) 該馬達兩個端子之間；(c) 供電顯示的電流。壓降 = (a) − (b)。
- 量三種狀態：輪子架空空載、輪子著地加壓重（有負載）、turbo 區間（命令 108 以上，最短時間內讀）。不要堵轉。
- 判讀：資料手冊（憑記憶，未重新查證）L298 總壓降 1 A 典型約 1.8 V、2 A 最大約 4.9 V，所以預期空載約 1.5~3 V，負載越大越多。(b) ≤ 12 V 表示馬達端沒超過額定；(b) > 12.5 V（我自己抓的判斷線，不是規格）就先停下來重新評估 14.5 V，不要往下做。

**1. 在新電壓下重量 duty → rpm（前饋表會整張移動，舊表是約 14 V 的）**
```bash
# 燒 car2_hwpwm_openloop（開迴路致動器），然後：
python firmware/car2/investigations/2026-10-hw-pwm-test/host_tools/calibrate_hw.py all 14v5
python firmware/car2/investigations/2026-10-hw-pwm-test/host_tools/build_lut.py 14v5      # 印出新的 FF_LUT_* 與和現行表的比較
```
把輸出的三個陣列貼進 `car2_car_control.ino`（和 10/10 下午做的一樣）。記下 **duty 255 與 duty 250 的轉速**——這決定 turbo 實際能到多快。同時看起轉門檻、維持下限有沒有移動（`MIN_RUN_DUTY` 62、`KICK_DUTY` 105 可能要跟著調）。

**2. 燒正式版（turbo 版），先確認一般模式沒壞**
```bash
python firmware/car2/investigations/2026-10-driver-debug/host_tools/usb_drive.py "25,25,3;0,0,2;50,50,3;100,100,3;0,0,2.5" out.tsv
```
預期 100% 仍約 270 rpm（誤差 ≤ 2%）。這一步 turbo 還沒被觸發。

**3. 跑 turbo 檢查（先降低上限）**
```bash
python firmware/car2/investigations/2026-10-turbo-14v5/host_tools/turbo_check.py turbo_108.tsv --max-cmd 108 --i-confirm-wheels-lifted
python firmware/car2/investigations/2026-10-turbo-14v5/host_tools/turbo_check.py turbo_112.tsv --max-cmd 112 --i-confirm-wheels-lifted
```
看：(a) turbo106 / turbo112 的穩態轉速比基線高多少；(b) `hold112` 是不是約 3 s 後 `turboState` 1→2、轉速夾回基線；(c) `back100` 約 5 s 後 2→0；(d) `again112` 是不是只有約 1.5 s。同時量：**供電電流峰值、L298N 與馬達溫度**（連續做三輪之後再量一次）。

**4. 決定怎麼用**
- 如果 duty 250 的轉速 ≥ 300：`TURBO_CMD_MAX_PCT`、`TURBO_FF_DUTY_CEILING` 維持；命令 112 ≈ 300 rpm。
- 如果還不到：選擇是（i）接受 turbo 上限就是 duty 250 的轉速；（ii）把 `TURBO_FF_DUTY_CEILING` 調到 253~255（**沒有 PID 餘裕**，轉速隨電池掉）；（iii）電壓再往上調（回到上面第 0 步的風險）。
- 地面測試之前要在地面負載下重量前饋表、重測 KI 與 kick。

**5. Orin 端（另一個 repo，這次沒動）**
`uart_bridge_node` 的 `max_wheel_speed` 被夾在 0~100，所以現在 ROS 這條路送不出 >100。要用 turbo 需要在 Orin 端決定怎麼觸發（例如 `/cmd_vel` 的另一個旗標或比例），並在該端也做時間限制。韌體端的保護是最後一道，不是唯一一道。

## 已知風險與沒驗證的

- 全部沒上板驗證：時間限制的實際行為、轉速、電流、溫度、供電壓降。
- 14.5 V 下 L298N、馬達、Orin / BMduino（如果共用電源）的耐受沒有查過規格，只查了馬達額定。
- turbo 狀態不在 STA 裡，Orin 看不到「被夾回」——它只會看到轉速比命令低。要不要加 `tb` 欄位是協議變更，等你決定。
- 限速 12 duty/20 ms 與 turbo 的瞬間電流沒量。
