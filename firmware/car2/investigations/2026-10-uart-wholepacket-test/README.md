## 測試腳本本身修正過的三個量測錯誤

實驗過程中，我自己的判定邏輯有三個錯誤，造成早期幾輪誤判為 FAIL，已修正後重跑：（1）停止指令的 byte 數用 `seq 0` 估算，實際 seq 是 3 位數；（2）停止指令沒記進送出紀錄，造成 `ackseq` 落後被算成 65535；（3）「`ackseq` 落後幾包」的單位是包，頻率越高越吃虧，改成以毫秒計；且停止後的閒置期 `ackseq` 不再前進，必須排除。以上都與通訊品質無關。硬指標（送收數量、byte 數、各種錯誤計數）從第一次執行起就一致。

## 結論與建議

1. **穩定性：八種送法沒有可偵測的差異**，在這個條件下都是零錯誤。所以選擇依據是速度、尾端延遲、對 BM 的負擔與簡單度。
2. **最快且最簡單：整包單一 `write()`，不加 `flush()`。** 單包送出 0.03 ~ 0.05 ms，約為現行分段法（約 15.9 ms）的 1/380 ~ 1/470；沒有 `sleep`，所以沒有排程抖動，也不會在 ROS timer callback 裡阻塞。
3. **不要加 `flush()`**：每次要等硬體排空，單包反而要 10 ms。
4. **頻率：** 控制上 50 Hz 已足夠（韌體 PID 與 PCA9685 都是 50 Hz）。實測 ≤ 200 Hz 對 BM 沒有可見負擔，≥ 400 Hz 開始拉長 BM 迴圈。**避免突發**（多包不留間隔連續送）。
5. 若因故必須保留分段：5 byte / 0.5 ms 在負載下仍零錯誤，單包約 4.6 ms，是折衷選擇；16 byte / 0.5 ms 約 1.3 ms。

## 仍然沒涵蓋的

- **輪子離地、馬達空轉**，電流小於實際行駛。馬達在地面負載下的電氣雜訊可能更大。
- **只往前轉到 60%**，沒有測反轉與全速。
- **CPU 負載是人造的忙碌迴圈**，不是真正的感知程式（它還會用到 GPU、記憶體頻寬與 DDS 流量）。
- **用的是測試腳本，不是 `uart_bridge_node`。**
- **端到端延遲沒有直接量測**（需要共同時鐘）。「單包送出耗時」只是 Orin 端把資料交給序列埠驅動的時間，加上線上時間約 0.9 ms 與 BM 迴圈處理。
- 全部在實驗室台上，約一小時內完成。

## 附帶觀察：BMduino → Orin 的 STA 偶有壞包（與 CMD 送法無關）

馬達轉動的所有輪次中，Orin 端收到的 STA 有 16 個壞包（checksum 或格式不符）/ 4,778 個（正常 + 壞包），約 0.33%；第一輪馬達沒轉時是 0 / 1,078。壞包在各種 CMD 送法下都有出現，沒有隨送法改變。這個方向仍由韌體分段送出（本次未改）。推測是馬達電氣雜訊，**未驗證**。checksum 有擋下來，Orin 端的轉向控制不使用 STA，只用在里程與故障閘門，但若之後要依賴 STA 做快速回授，這個比例值得留意。

# 第四輪：方法 B，直接量 BMduino 收到幾包（2026-10-08 下午）

**條件：** 輪子離地；BMduino 燒 `car2_car_control_rxcounters`；Orin 跑改成整包送出的 `uart_bridge_node`（`feature/uart-send-whole-20261008`）；馬達依 0 → 40% → 60% → 40% → 0 循環空轉（最高約 180 rpm），前輪 ±8° 擺動；Orin 電源模式 `MAXN_SUPER`。

**判定法：** 韌體每 200 ms 把 STA 與 dbg 合成同一則 USB 訊息，兩者是同一瞬間的快照。bridge 的 `seq` 從 0 起、每包 +1，BMduino 每次重開機（開啟序列埠就會）計數歸零，所以沒有掉包時**每一則訊息都必須滿足 `bmCmdOk == ackseq + 1`**；中途少收任何一包，差值就會永久變負。不需要 Orin 端自己數送了幾包。

| 階段 | 條件 | CMD 數 | `bmCmdOk == ackseq+1` | csFail / abort / overflow / FE / I2C | STA 壞包（BMduino → Orin） |
|---|---|---|---|---|---|
| B1 | bridge 10 Hz（預設），無感知，5 分鐘 | 3,074 | 1,724 則全部成立 | 全 0 | 1 / 1,525（0.07%） |
| B2 | bridge 50 Hz，無感知，5 分鐘 | 15,373 | 1,724 則全部成立 | 全 0 | 9 / 1,524（0.59%） |
| B3 | bridge 10 Hz + 真正的感知節點（相機、depth_bev、除錯串流），5 分鐘 | 3,073 | 1,926 則全部成立 | 全 0 | 5 / 1,526（0.33%） |

三輪合計 **21,520 個 CMD，一包不少**；PCA9685 全程就緒，無馬達故障旗標，BMduino 沒有重開機。

**附帶觀察：** STA 壞包比例在馬達轉動時為 0.07% ~ 0.59%，馬達沒轉的台上測試是 0 / 1,078；50 Hz 那輪最高。這個方向仍由韌體分段送出（未改），被 checksum 擋下，與 CMD 的結論無關，成因未驗證。

**腳本（`host_tools/`）：** `ros_method_b.sh`（Orin 端：啟動 bridge、選擇性啟動感知、跑速度曲線、記錄 link status）、`ros_cmd_vel_profile.py`（Orin 端：發布受控的 `/cmd_vel` 曲線，輪速硬上限 60%）、`usb_method_b.py`（電腦端：讀 USB 並做上述判定）。

**沒涵蓋的：** 地面行駛（馬達帶負載）、輪速超過 60%、反轉、超過 5 分鐘的長時間運轉、Orin `25W` 電源模式。
