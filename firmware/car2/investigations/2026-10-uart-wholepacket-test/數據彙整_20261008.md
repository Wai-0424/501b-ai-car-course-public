# 2026-10-08 UART 通訊測試數據彙整

車2 Orin → BMduino 的 CMD 由「分段送出」改為「整包單一 `write()`」的比較實驗與 ROS 實測。本文所有數字由 `host_tools/compile_results.py` 從結果檔與原始紀錄計算，原始資料都在 `results/`。

## 二、結論摘要

1. **整包單一 `write()` 零掉包。** 所有有效執行合計 **109,274 個 CMD、4,506,780 byte**，BMduino 端收到的合法 CMD 數與 byte 數都等於送出數，checksum 失敗、frame 被打斷、frame 溢位、framing error、I2C 錯誤全為 0（其中馬達轉動的台上測試 76,605 個，ROS 方法 B 21,520 個）。
2. **單包送出耗時從約 15.93 ms 降到約 0.042 ms**（50 Hz、馬達轉動下的平均值，約 1/379）。整包 + `flush()` 反而要約 10.03 ms，不要加。
3. **穩定度在八種送法之間分不出高下**（都零錯誤），所以選擇依據是速度、尾端延遲與對 BMduino 的負擔。整包在 100 / 200 / 400 / 600 Hz 都零錯誤，找不到天花板；但頻率 ≥ 400 Hz 或多包連續送（突發）會讓 BMduino 的 `pollLink` 區段單次最長耗時從約 1.1 ~ 1.4 ms 拉到 3 ~ 5 ms（軟體 PWM 會凍結這麼久）。
4. **ROS 實測（方法 B）：** bridge 10 Hz、50 Hz、10 Hz + 真正感知節點各 5 分鐘，共 21,520 個 CMD，每一則 USB 訊息都滿足 `bmCmdOk == ackseq + 1`（一包不少）。CMD 預設頻率改為 30 Hz 後，`ros2 topic hz` 量到 30.001 Hz。
5. **觀察到的小問題（與 CMD 送法無關）：** BMduino → Orin 的 STA 壞包，馬達轉動時台上腳本共 16 / 4,778（0.33%），馬達不轉的第一輪為 0 / 1,078。這個方向仍由韌體分段送出（未改），被 checksum 擋下。成因未驗證。
6. **沒涵蓋：** 地面行駛（馬達帶負載）、輪速超過 60%、反轉、超過 5 分鐘的長時間運轉、`25W` 電源模式、30 Hz 下的方法 B。

## 六、方法 B：直接量 BMduino 收到幾包

**判定法：** 韌體每 200 ms 把 STA 與 dbg 合成同一則 USB 訊息，兩者是同一瞬間的快照。bridge 的 `seq` 從 0 起、每包 +1，BMduino 每次重開機（開啟序列埠就會）計數歸零，所以沒有掉包時每一則訊息都必須滿足 **`bmCmdOk == ackseq + 1`**；中途少收任何一包，差值就會永久變負。
