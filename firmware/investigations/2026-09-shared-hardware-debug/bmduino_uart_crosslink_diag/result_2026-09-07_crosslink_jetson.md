# BMduino <-> Jetson Orin 跨裝置 UART 測試記錄(2026-09-07)

- 硬體:BMduino-UNO(BM53A367A/HT32F52367)Serial1(PC12 TX/PC13 RX) <-> Jetson Orin `/dev/ttyTHS1`,115200 baud,經 74125 三態緩衝器
- 測試腳本:`bmduino_uart_crosslink_diag.ino` + Jetson 端 `jetson_uart_crosslink_diag.py`
- 協定:`[1 byte 長度 L][L byte 內容]`,內容為跟位置相關的可辨識字元(0-9A-Za-z 循環),長度掃 1~32

## Run 1 — 74125 未供電

- Phase A(BM→Jetson):Jetson 只收到 13/32 筆,BM 自己 Phase A 期間卻有 `rxdrCount+=54`(理論上該階段 Jetson 不送資料,不該有事件)
- Phase B(Jetson→BM):BM 第一筆讀到長度前綴 32(剛好是 Phase A 自己最後送出的長度),之後全部逾時收不到
- 判斷:BM 自己的 TX 訊號迴授回自己的 RX,懷疑 74125 缺電導致三態輸出浮接/雜訊

## Run 2 — 74125 供電後,BM 端仍用嚴格逐一對應的讀取邏輯

- Phase A(BM→Jetson):Jetson 收到 29/32 筆(未收滿是監聽逾時,不是資料錯),**全部 PASS,零損毀**
- Phase B(Jetson→BM):BM 前 17 筆完全沒收到(`rxdrCount` 精準對應少了 170 byte),但第 18~32 筆長度精準吻合,**內容完全正確**
- 判斷:自我迴授問題已解決(Phase A rxdrCount 歸零);Phase B 的「前段遺失」判斷為測試腳本兩側時間沒對齊,不是資料損毀(遺失是整段不存在,不是內容跑掉)

## Run 3 — BM 端改成跟 Jetson 端一樣的「掃描找封包開頭」邏輯,不假設固定順序

- Phase A(BM→Jetson):**32/32 全部 PASS,完全乾淨**
- Phase B(Jetson→BM):前 9 筆沒收到(比 Run 2 的 17 筆進步),但收到的第 10~32 筆(lenByte=10~32)**全部 PASS,逐 byte 完全正確**
- 「前段遺失」的筆數從 17 降到 9,隨著測試腳本同步時機改善而縮小,支持這是測試工具兩端啟動時間沒對齊造成的,不是韌體/驅動問題

## 結論

**三次測試中,只要 74125 有供電、且封包真的到達,內容從來沒有損毀過**(不管是 BM→Jetson 還是 Jetson→BM 方向,長度涵蓋 1~32 byte 全部驗證過)。這跟原本觀察到的「內容變成固定值 0x00/0xFF」完全不同——這次遇到的問題是「一段資料完全没到達」,不是「到達了但內容被換掉」,而且已知的原因是 74125 缺電。

**目前最合理的推測:原本觀察到的 UART 資料損毀,很可能主要是那顆 74125 緩衝器供電/接線問題造成的,不是 `HardwareSerial.cpp` 驅動層的邏輯缺陷。** 這跟先前自我迴接測試(TX 假說沒重現)、以及這次跨裝置測試(供電修好後兩個方向都乾淨)兩份證據方向一致。

## Run 4 — 用正式的 `<CMD,...>`/`<STA,...>` 協定重現測試(`bmduino_uart_test.ino`,74125 已供電)

- 場景:Jetson 持續每 100ms 送一次 `<CMD,fwa 0,bwl 0,bwr 20>`(25 byte),BM 每 100ms 自動送一次 `<STA,S1 -1>`,共跑 20 秒
- **Jetson 端(收 BM 送來的 STA)**:20.9 秒內連續收到 209 個 frame,**209/209 全部乾淨、0 個異常**,時間戳顯示全程沒有中斷
- **BM 端(收 Jetson 送來的 CMD)**:凡是 BM 開始接收之後,連續 112 個 CMD 封包(約 11.2 秒份)**逐 byte 完全正確**——`feBM` 全程 0(framing error 一次都沒有),`rxdrBM` 精準每次 +25(剛好是 CMD 封包長度,沒多沒少),`[actuator]` 解析出來的值每一次都精準是 `fwa=0 bwl=0 bwr=20`,沒有任何一次錯誤
- 112 筆之後 `rxdrBM` 不再增加、~500ms 後失效保護正確地把 `bwr` 歸零——這不是通訊中斷,是因為 BM 這次晚於 Jetson 才重置開機(兩支測試程式分別在不同機器手動啟動,沒有嚴格同步),Jetson 自己送完 200 次 CMD 後自然停止,BM 只是照設計正確反應「一段時間沒收到新指令」

### 結論(目前為止最終版)

**兩個方向、在雙方真正有在通訊的整段時間內,完全零損毀、零 framing error。** 這是繼「自我迴接測試沒重現 TX 假說」、「跨裝置簡化協定測試乾淨」之後,第三份、也是最貼近原始故障場景(真正的 CMD/STA 協定 + 真正跨裝置)的乾淨結果。

**目前的結論:原本觀察到的 UART 資料損毀,根因是 74125 緩衝器沒有供電,不是 `HardwareSerial.cpp` 驅動層的邏輯缺陷。** 供電修好之後,三種測試方式(自我迴接、簡化診斷協定跨裝置、正式協定跨裝置)都沒有再重現任何內容損毀。之前在原始碼裡找到的臨界區保護缺失、RX 端雙重讀暫存器等,雖然是程式碼裡真實存在的瑕疵、原則上仍建議之後有空修掉,但目前沒有證據顯示它們是造成當初那次資料損毀的原因。
