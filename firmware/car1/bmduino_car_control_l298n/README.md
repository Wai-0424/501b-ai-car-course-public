# 車一 BMduino L298N 控制韌體

這是車一的獨立控制韌體。2026-10-10 已用 e-Link32 Pro 刷寫並在車輛架高、輪胎無負載時完成雙輪 PID、正反轉、低速與逾時停車測試。PID 參考車二的 20 ms 更新、前饋查表與輸出斜率限制；車一的最高指令速度原為 180 RPM；2026-11-17 起改為 280 RPM（見下方「2026-11-17」一節）。

**刷寫狀態（2026-10-13）：** 已用 e-Link32 Pro 刷入本檔對應的版本（`build/car1_l298n_car2comm`）。內容：改良版換向保護（至少 300 ms 且編碼器連續 3 個 20 ms 週期低於 5 tick）已實測，反向 duty 在輪速降到約 4–8 RPM 時才恢復（舊版在 46/53 RPM 就恢復）；`bwl` 改成左輪（M2）、`bwr` 右輪（M1），與車二語意一致；通訊層比照車二（Serial3 460800、STA 20 Hz、car2 欄位）；PID 預設 Kp 1.5。

**2026-10-13 編碼器與左馬達：** M2 編碼器改接 D10／D11；舊左馬達的 A 相每圈漏約 15%（A／B 跳變比固定 0.85，與速度無關，焊接與換腳位都沒改善），已更換左馬達，換後 M1、M2 的 A／B 比都是 1.00。兩輪的每轉 tick 數維持 1560（換算後兩輪同 duty 的速度相差 4% 以內）。前饋表已用新馬達重量（兩輪同時、硬體 5 kHz PWM、由高往低掃的維持曲線）。目前 Kp 1.5 / Ki 0.04 / 積分上限 300 / 斜率 8：兩輪階躍（30→60→30→100→50→15）起步過衝 1–5%、整定約 0.6–1.0 s，降速階躍欠衝 5–10%、整定約 1.9 s（尚未再改善）；Kp 2.0 差異在雜訊內，Kp 2.5 過衝 12–15%。以上都是架高無負載結果。

| 功能 | 車一實測接線 |
|---|---|
| M1／右輪（`bwr`） | PCA9685 CH1/CH2 → L298N IN1/IN2；BMduino D8 → ENA；encoder D2/D3 |
| M2／左輪（`bwl`） | PCA9685 CH3/CH4 → L298N IN3/IN4；BMduino D9 → ENB；encoder **D10（A）/D11（B）**（2026-10-13 起，原 D6/D7） |
| PCA9685 | Wire1，I2C `0x40`，CH0 為前輪轉向 |
| Orin UART | Serial3，**460800 baud**（Orin 端 `serial_baud` 要同步）；本機 USB 115200 亦可測試 |

D8/D9 用 BMduino `analogWriteFrequency(5000)` 的硬體 PWM，經 74LS14 雙級緩衝到 L298N Enable。方向腳由 PCA9685 輸出。上電先設 Enable=0；PCA9685 離線、編碼器長時間無回授或命令逾時也會關閉 Enable。候選版換向時先關閉 Enable、方向腳拉低，至少等待 300 ms 並依編碼器判斷接近停轉；這是空轉等待，並非主動煞車。

## 超速煞車（2026-11-03，下坡用）

**已刷入**（`build/car1_l298n_brake`）。原本實際輪速比目標快時只會把驅動 duty 調小，Enable 關掉也是滑行；前饋讓 duty 要到超速約 190 RPM（低指令）以上才會降到 0，所以下坡時等於繼續推著馬達。現在輪速（沿目標方向、已濾波）超過目標 `bon`（預設 6 tick/20 ms ≈ 11.5 RPM）就進入煞車：方向腳同電位、Enable 給煞車 duty = `bkp × (超速 − boff)`，夾在 30 ~ `bmax`；降回目標 +`boff`（預設 2 tick ≈ 3.8 RPM）以內才離開（遲滯）。離開時從 PID 當下想要的驅動 duty 重新斜坡，煞車中積分凍結。指令為 0、逾時、堵轉的行為沒變（仍是滑行）。

| TUNE 參數 | 預設 | 範圍 | 說明 |
|---|---|---|---|
| `brk` | 1 | 0/1 | 煞車開關 |
| `bon` / `boff` | 6 / 2 | 1~40 / 0~40 | 進入／離開的超速門檻（tick/20 ms，×1.92 = RPM） |
| `bkp` | 8 | 0~30 | 煞車 duty／超速 tick |
| `bmax` | 128 | 30~255 | 煞車 duty 上限（約 50%） |

**沒有電流感測**，`bmax` 只限制 PWM，不能保證峰值電流低於 L298N 煞車的 2 A 限制；上調前要先量電流。USB 的 dbg 行後面多了 `brakingL,brakingR,brakeCyclesL,brakeCyclesR,brk,bon,boff,bkp,bmax`。煞車中 `dutyL/dutyR` 顯示的是煞車 duty。

**架高實測（2026-11-03，`tools/car1_brake_test.py`，資料在 `tools/pid_data/brake_20261103/`）：** 100%（≈180 RPM）降到 15%（目標 72.7 RPM），煞車關／開各 5／6 次：整定到 ±5% 帶內 2.3–2.45 s → 0.95–1.3 s，穩態誤差 −4~−7 RPM → −0.3~+2 RPM，最低點無明顯欠衝（63–68 RPM）；每次煞車約 31–33 個 PID 週期（0.65 s），穩態沒有誤觸發。**這只證明「被外力推快時能主動拉回目標」，不是持續下坡力：架高輪子沒有重力負載，坡上能不能長時間 hold 在目標、`bmax=128` 夠不夠、煞車電流多大，都要上坡測。** 另有一次（第一輪煞車開）起步段轉速曲線異常（高速段只到約 123 RPM，像中途重啟），之後 9 輪（含 upms 重啟偵測）都沒再出現，原因不明。

### CMD `brk` 欄位與煞車力放寬（2026-11-09，已刷入）

編譯目錄：`build/car1_l298n_brk_cmd_20261109`。起因：Orin 端 11/9 下坡紀錄顯示 `dutyL/dutyR` 釘在 128（= 當時 `bmax`，煞車飽和）仍從約 100 rpm 加速到約 350 rpm。

- CMD 新增可選欄位 `brk N`（0/1），寫法同 `led`：沒帶維持上一個值，不認得的值忽略；**開機預設 0，CMD 逾時 500 ms 一律歸 0**。`brk 0` 時沒有任何煞車。**所以現有只送舊 CMD 的 Orin 程式，刷入這版後不會再有煞車，必須先送 `brk 1`。**
- `bmax` 預設 128 → 255（仍可用 USB TUNE 調）。新增煞車 duty 上升率限制：每 20 ms 最多 +32（`BRAKE_RISE_STEP`），剛進入煞車從 30 起算。
- STA 的 `brk` 位元改成：bit0 = M1（右輪）煞車中、bit1 = M2（左輪）煞車中、bit2 = M1 恢復滑行、bit3 = M2 恢復滑行、bit4 = 煞車功能啟用。煞車時 `dutyL/dutyR` 是 Enable 實際 PWM。
- 只用短路煞車（Enable 高、IN1=IN2 低），沒有反向通電。進入／離開門檻、`bkp`、停轉鎖、換向保護都沒改。
- **架高台架實測（`tools/car1_brake_bench.py`，資料在 `tools/pid_data/brake_bench_20261109/`）：** 先轉 3 s 再切換，量 vL、vR 都 < 60 rpm 的時間。從 100%（180 rpm）：0% 滑行 0.6–0.85 s、1% brk 0 為 1.0–1.2 s、1% brk 1 `bmax=255` 為 0.3–0.4 s（快 2–3 倍）、`bmax=128` 為 0.6–0.7 s。從 40%（106 rpm）：滑行 0.45 s、`bmax=255` 0.40 s，沒有快 2 倍（輪子在空中慣量小，低速時短路煞車力也小）。所有條件 `f` 都是 0，單輪測試的 brk 位元對應正確（右輪 17、左輪 18）。CMD 停止送出後 0.55 s 內 duty 歸 0、煞車位元清除（500 ms 看門狗）。
- **未驗證：** 100% duty 的煞車電流、L298N 發熱、10 分鐘連續跑（`bad_STA`、`f=4`）、地面行駛、實車下坡能壓到多少 rpm。台架輪子在空中沒有重力負載，上述時間不能直接換算成坡上的終端速度。

### 退出煞車銜接修正（2026-11-03，已刷入）

編譯目錄：`build/car1_l298n_brake2`（已用 e-Link32 Pro 刷入）。上面的架高實測屬於原版。

**修正版架高實測（`car1_brake_test.py --label t5`，100%→15%，目標 72.7 RPM，煞車關／開各 3 次）：** 煞車開時左輪整定 1.33–1.35 s（原版 0.95–1.3 s）、右輪 2.35–2.43 s（原版同為約 1 s）；降速後最低點左輪 47–48 RPM、右輪 39–42 RPM（目標 −35~−46%，原版沒有欠衝）；最後 1 s 平均高出目標 +2.3~+4.4 RPM。煞車關的對照組與原版相同（2.35–2.45 s、−5~−7 RPM）。原因：退出煞車後滑行到目標以下才從零 duty 以每 20 ms 8 的斜率恢復，輪子在恢復期間降到低於目標很多。要避免這段欠衝，恢復起點需要比零高（例如以當下實際輪速查前饋表），但這會回到原版「恢復時推車」的取捨；是否調整由你決定。

**測試腳本注意：** 這版 STA 變長，USB 單行輸出（STA＋每 4 則一行 dbg）已佔滿 5 B/ms 的送出頻寬，`staSkipUSB` 在測試中累計約 57–60。舊版 `car1_bm.Car1.poll()` 沒有時間上限，會讓 CMD 餓死、超過 500 ms 韌體就歸零（t4 的「轉速掉到 0」是這個測試腳本問題，不是韌體堵轉），已加上 `budget` 修正。

- 原版退出煞車時先把 `dutyOut` 重設為 `feedforward + Kp*error`，再以此為斜率限制基準；因此實際會直接恢復約 90–104 的驅動 duty（最低目標附近，未計積分），並非從零逐步恢復。
- 修正後先清除殘留積分、輸出歸零；輪速仍超過目標時維持滑行，若再次超過進入門檻則恢復主動煞車。降回目標以內，才從零依原本每 20 ms 最多 8 duty 恢復驅動。
- 進入煞車或退出回驅動的橋狀態切換，先實際關閉該輪 Enable，再寫方向腳，避免上一個模式的 PWM 暫時套用到新的方向狀態。
- 零指令、逾時轉成零指令、堵轉、換向等待及 PCA 離線，都立即清除煞車／恢復狀態；原本的滑行停止、轉向與保護語意維持。
- 進入／離開門檻仍是 6／2 tick，`bkp=8`、`bmax=128`；沒有增加煞車功率或改變 55–180 RPM 映射。這次修正不能保證解決持續下坡時煞車 duty 已飽和仍加速的問題。
- STA 尾端增加整數 `brk` 與 `bmax`。`brk` 是位元遮罩：1=左輪主動煞車、2=右輪主動煞車、4=左輪恢復滑行、8=右輪恢復滑行、16=煞車功能啟用。例如 19 表示功能啟用且兩輪煞車；28 表示兩輪恢復滑行。`bmax` 是當下煞車 PWM 上限；搭配煞車旗標與 duty 可判斷是否飽和，但不能代替電流量測。
- 舊 STA 欄位順序與 checksum 維持；Orin 現有 parser 可接受並保留新增數值欄位。現有事件記錄若只選固定欄位，仍需另外接入 `brk/bmax` 才會記在事件 CSV 中；本次只修改本機韌體，沒有部署 Orin。

### recovery v3（2026-11-03，編譯候選，待使用者刷入）

編譯目錄：`build/car1_l298n_brake_recovery_v3_20261103`。以上 `t5` 實車架高數據屬於 v2；以下是依該結果修正的新候選版本，尚未實車驗證。

- 退出煞車後，濾波輪速或原始輪速仍高於目標時都保持滑行。確認兩者降回目標後，以**當下濾波輪速**查該輪的前饋表作為恢復起點，上限為目標輪速的前饋值，之後繼續原 PID 與每週期 8 duty 的斜率限制。這個恢復起點刻意高於零，避免 v2 從零斜坡造成的深度欠衝；不能視為已證明下坡更穩定。
- 清除煞車前的積分，保留切換模式前實際關閉 Enable 的做法。當下輪速已為零或反轉時，仍由零 duty 起步。
- 進出煞車門檻、增益、上限均未改動（6/2 tick、Kp 8、最大 duty 128）。本次沒有處理持續重力負載下的最大制動能力。
- ORIN UART 保持 20 Hz STA、5 bytes/ms 分段；USB 改為獨立 10 Hz STA、每 5 筆附 dbg（2 Hz），不再以 50 ms 的 USB 時槽容納約 77 ms 的 STA+dbg。STA 欄位沿用 v2，沒有再加長。
- 保留使用者加上的 `poll(budget)` 限時概念，改為讀取 `in_waiting` 已到達的 bytes 並跨呼叫保存半行，避免長 STA 被 20 ms `readline()` timeout 切斷丟失。持續資料流也會在時間預算後返回呼叫端，讓 CMD 可繼續送出。測試程式優先記錄同筆 STA 的 `brk`，舊版才退回較慢的 dbg 旗標。
- 離線通過 27 項實際 PID／傳送排程檢查，以及 6 項假串口接收測試。在每 1 ms 執行傳送的模擬下，包含 dbg 突發資料仍維持 BM 20 Hz／USB 10 Hz，兩路 skip 均為零。這不是硬體串口時序或馬達性能驗證。
- USB 取樣降為 10 Hz，架高整定時間約有 0.1 秒取樣解析度；比較版本時應保留取樣頻率與量測視窗資訊。

## 安全車燈（2026-10-27/29）

兩條 WS2812B（各 8 顆）：**D5 = 橘燈、D7 = 白燈**（常數 `PIN_LED_ORANGE`／`PIN_LED_WHITE`，接反時對調）。驅動方式與時序照抄車二的 `ledShow`（直接寫 GPIO 暫存器 + 忙等迴圈）。模式由 Orin 用 CMD 的 `led` 欄位切換，編號與車二相同；閃爍／呼吸節奏由韌體自己產生，STA 在 `f` 後回報 `led <實際生效的模式>`。

| `led` | 效果 |
|---|---|
| 0 | 全滅 |
| 1 | 白燈恆亮（開機 2 s 內的預設，可看出韌體活著） |
| 2 | 橘燈＋白燈同步 3 Hz 閃爍（巡航） |
| 3 | 白燈呼吸、橘燈熄滅（待機） |

沒帶 `led` 就維持上一個模式，不認得的值忽略。開機 2 s 後仍沒收過 CMD，或 CMD 逾時 500 ms，一律強制 3。Orin 端（`bridge_core.py`）：輪速指令不為 0 或 `|vL|`、`|vR|` > 5 rpm 送 2，兩者都靜止連續 1 s 送 3；ROS 參數 `led_enable`、`led_idle_hold_sec`、`led_idle_rpm_threshold`，並發布 `/car1/led_cmd`（送出）與 `/car1/led_state`（STA 回報）。

已知影響：每次更新燈會關中斷約 30 µs × 8 顆，UART 路徑的 STA 壞封包比無車燈版略多（10/29 對照：閃爍版約 14 個／58 s，無車燈版約 8 個）。

## 通訊與速度定義

```text
<CMD,seq 42,fwa 0,bwl 30,bwr 30,cs XX>
<STA,ackseq 42,S1 -1,rpmL 92.1,rpmR 93.0,vL 92,vR 93,f 0,dutyL 141,dutyR 138,posL 2776,posR 6365,unit 0,upms 1234,cs XX>
```

STA 前七個欄位與車二相同（Orin 的 `uart_protocol.parse_sta()` 已用車二 Orin 上的版本實測可解析）：`rpmL/rpmR` 為 PID 濾波後的輪速（沿目標方向為正，指令 0 時為 0）；`vL/vR` 為常駐速度（整數 rpm、前進為正，手轉/滑行/被推也看得到）；沒有收過有效 CMD 時 `ackseq` 為 -1。後面是車一專屬欄位：`dutyL/dutyR`、`posL/posR`（原始計數，前進為正）、`unit/upms`。STA 每 50 ms 一則；上一則尚未送完則略過並計數（`staSkipBM`）。

`cs` 是封包內容（不含 `<`、`>` 與 `,cs XX`）逐 byte XOR 的兩位十六進位數。`seq` 與校驗碼都有效才套用命令、更新 `ackseq` 與 500 ms watchdog。**`bwl` 控制左輪＝M2、`bwr` 控制右輪＝M1**，正值為車輛前進方向（2026-10-13 起；先前版本 `bwl` 驅動 M1／右輪）。`fwa` 為轉向命令。非零速度百分比 1–100 對應約 55–280 RPM（2026-11-17 起；之前為 180），0 立即關閉 Enable；所以 30% 指令約 121 RPM，並非 duty 30%。

`f` 是 bit mask：1=左輪（M2）無編碼器動作，2=右輪（M1）無編碼器動作，4=PCA9685 離線，8=PID 校正鎖仍開啟。故障輪需持續零命令 300 ms 才解除停轉鎖。

**USB 診斷與調校：** USB 每則 STA 後每 4 則附一行 `dbg,cmdL,cmdR,dutyL,dutyR,steerCalls,steerErr,dirCalls,dirErr,pcaReady,staSkipBM,staSkipUSB,maxLoopGapUs,cmdCsFail,kp,ki,lim,slew`。USB（不含 Orin UART）接受 `<TUNE,kp 1.5,ki 0.04,lim 300,slew 8,cs XX>` 暫時改寫 PID 參數，重開機回到預設；測試腳本為 [car1_pid_steps.py](../tools/car1_pid_steps.py)（共用函式在 [car1_bm.py](../tools/car1_bm.py)）。舊的 PowerShell 腳本解析的是舊 STA 欄位順序，需更新後才能再用。

目前兩輪都**暫用 1560 tick／輸出軸轉**計算速度及位移，依使用者指定作為 PID 階段的假設。先前 M2 手轉十圈有約 1320 tick／轉的紀錄，兩者尚未用獨立轉速計或示波器釐清。因此報告中的 RPM 是依 1560 換算的編碼器轉速，實際機械 RPM 仍需再確認。架高測試也不能取代落地、負載與電池電壓變化下的測試。

建置／刷寫：

```powershell
arduino-cli compile --fqbn HT32:HT32:BM53A367A --build-path build/car1_l298n_car2comm firmware/car1/bmduino_car_control_l298n
arduino-cli upload --fqbn HT32:HT32:BM53A367A --input-dir build/car1_l298n_car2comm
```
